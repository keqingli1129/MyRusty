Intro
Rust is type safe, memory safe and thread safe –  but that doesn't mean you can't have deadlocks,  
or livelocks, or crashes, you absolutely can. The  difference is that when a Rust program crashes,  
it's a clean abort. There's no  chance of malicious code execution,  
the process just stops. In  Rust that's called a panic.
There are plenty of things that can cause a panic:  
integer division by zero, out-of-bounds  array access, a failed assertion.  
We do our best to make sure these conditions  can't happen, but sometimes they do anyway.
In fact, remember println Hello World?  Well, it actually has a crashing bug.
Welcome to lesson 3, and thank you for  supporting what I'm doing here. In these  
premium videos I want to delve further into the  practice of Rust; and today we're talking about  
panics. This might seem like an odd thing to  cover so early on, but I have a few reasons:
First, Rust's use of panics is an important  part of how it achieves its safety guarantees.  
It's quite different from the C or C++ approach  of letting you slide into undefined behaviour  
if you index off the end of an array.  Rust might seem somewhat panic-happy,  
and I want you to understand what that  means, rather than being put off by it.
Second, Rust APIs are built to  strongly encourage you to handle  
error cases. We'll get to proper  error handling soon, but for now,  
the easiest way to get at the data you want is  just to assert success - in other words to panic  
if an error happened. And of course that's fine  when you're messing around with toy programs,  
so a basic knowledge of panics will help  you get further in your explorations.
Third, I want you to be comfortable writing unit  tests right from the start. You've already seen  
tests that assert a function returns  the correct value. I'm also going to  
show you how to write a test that checks  a function panics when it's supposed to.
And last: Rust is made for building robust  software, and a proper understanding of  
panics and how to configure panic handling  will help you when it comes time to build  
something for real. The key decision  is whether your program should try to  
keep running after a panic; and the default  setting might not be the most appropriate.

Panic does what? Unwind vs Abort
Ok so a panic can be generated by the compiler,  like from integer overflow or indexing  
out-of-bounds, or it can come from library code  like the unwrap functions, or we can explicitly  
panic using macros. But regardless of what  caused it, what actually happens when we panic?
Well there are two options: unwind or abort, and  you get to choose. I don't just want to *explain*  
what those options mean, I want to show you. And  for that, we need a program that spawns multiple  
threads. Because the idea of unwinding a thread  is that the other threads can continue running.
So let's build a network service that uses a  separate thread to handle each client connection.
