In video 2, Hello Rust, we covered the  basic language syntax and the scalar types.

Tuples
We're doing tuples first because they're  simpler, and then we'll get to structs. Here's a function that returns an integer,  
an i32. What if we actually have two  different values that we want to return?  
Well we could declare a struct type with  a field for each of the values and return   that. But sometimes we don't want to bother with  all that, so instead we can just return a tuple.
The return type here is the tuple of an i32  and a bool. A tuple is a lot like a struct,  
except you don't need a type declaration. You  just write the fields separated by commas,  
put parens around it, and  you've got yourself a tuple. So to be clear, `(i32, bool)`  in parens is a type. And `(0,  
true)` in parens is an expression  that produces a value of that type.
Now, when you call foo and you get back a  tuple, how do you get at the individual fields? Well, a tuple is like a struct, except we don't  name the type, and we don't name the fields.
So the compiler gives the fields  names that look like integers. x.0   is the first field, the i32, and  x.1 is the second field, the bool.
Now I want to be clear here: A tuple  is not a list, it's not an array,   you can't index into it, you  can't iterate through it,  
because the fields can be of different  types. These field names look like integers,   but they're just the names the compiler invented  for the fields based on position in the tuple.
Destructuring tuples
It's perfectly fine to access fields  of a tuple this way with dot notation,   .0, .1, but it's often more convenient to  destructure a tuple into its individual fields.
So now we have a single let statement, with a  tuple pattern that creates the two variables  
`a` and `b`. `a` is assigned the integer and `b`  is assigned the bool, directly from the tuple.
Now, when you're learning a new language  it can take a while to get familiar with   which bit of grammar goes where, and this  is a great opportunity to highlight that  
there are three different things  here that all look like tuples. `(i32, bool)` is a tuple type. `(0, true)` is a  
tuple expression. It constructs a  value of that tuple type. And `(a,  
b)` is a tuple pattern that destructures  a tuple value into its individual fields.
These are three distinct pieces of grammar -  types, expressions and patterns. The language  
designers have made them look the same for  consistency, but they are different things.

And, maybe this is obvious but  I want to point it out anyway:   The expression is made up of simpler  expressions. `0` is an expression,

Structs
I did that whole section on tuples first  because tuples and structs are similar,   and in terms of how they're represented in  memory they're basically the same thing.
You have some fields, you glue them together  in a fixed layout, and you call it type. With structs we have the same idea of  packaging some fields together into a type,  
but structs add on all the other capabilities that  come with declaring a distinct name for that type.
Here's the Rust syntax for declaring our Point  struct, with x and y coordinates. Inside the  
curly braces we have a comma-separated  list of fields, and each field has a   name and a type. The trailing comma after  the last field is optional, but this is  
idiomatic style when you're writing one field  on each line. It's a bit more consistent,   and it means you don't have to edit  that line if you add another field.
To make an instance of a struct, you must provide  a value for every field. There's no such thing as  
uninitialised memory, or partial initialization,  unless you're in unsafe Rust. So we write the name  
of the struct, and inside the curly braces we name  each field and give it a value after the colon.  
This is an expression that constructs a value of  type Point, which we assign to the variable `p`.
Let's have a function that returns a Point. The  expression that constructs the Point is the final  
expression in the function, so that's what gets  returned. It's a matter of style whether you put  
all the fields on one line or on separate lines,  and whether you include the trailing comma. And  
just to avoid confusion here, the outer Point  curly-brace is the return type of the function,  
and the inner Point curly-brace is the start of  the expression that constructs the return value.
Once you have a struct, you can access its  fields using dot notation as you'd expect.   So we call origin, we get a Point and assign  it to p. And then we can access p.x and p.y;
Inherited mutability
Of course p is immutable by default, so  if I try to assign to p.x, I get an error.
We can declare p to be a mutable variable with  "let mut p", and now we can assign to the fields.
You can't have some fields that are mutable and  some that are immutable. The mutability of the  
whole struct is determined by the mutability of  the variable that's holding it. This is called  
"inherited mutability" - the fields inherit their  mutability from the variable holding the struct.
If you want to make a struct with an  interface where some fields are immutable,   what you really want is private fields, that are  only accessed through methods. We'll get to that.
Destructuring structs
So we've seen how to declare a  struct, how to construct a struct,   and how to access its fields.  What about destructuring a struct?
Just like with tuples, you can destructure the  fields of a struct into separate variables.  
This pattern matches a Point, and creates  two new variables, `a` and `b`. Field `x`  
is assigned to `a`, and field `y` is assigned  to `b`. So now we can print out `a` and `b`.
Now, this might seem like a strange thing  to do when we could just use p.x and p.y,  
but the fact that you can write a pattern that  gets inside a struct is occasionally quite useful,  
especially when the struct is buried  inside another type like an enum. What I want to highlight for now is, again,  this consistency in the language across these  
three parts of the grammar: types, expressions  and patterns. A struct type declaration builds  
up a new type from the individual types of  its fields. A struct expression builds up a  
value from the expressions for the values of  its fields. And a struct pattern matches the  
whole struct and destructures it, so we can  write patterns that access each of it fields.
Now, in this example I've chosen  the variable names `a` and `b` to   be distinct from the field names `x` and  `y`. But if you're happy with variable  
names that are the same as the field  names, then there's a shortcut for that. You don't have to say x colon x. You  can just say x, and you'll get a new  
variable with the value of field x.  So these two lines are equivalent.
A struct pattern doesn't have to create a variable   for every field. The underscore pattern  matches anything and ignores whatever is  
there. So this pattern makes the  variable `x`, but it ignores `y`.
You have to acknowledge all the fields in the  struct, even if you ignore their values. This  
pattern is a compile error because we  didn't mention y. And this is useful,  
because when you add a new field to a struct,  you probably want the compiler to bring your   attention to the places where you haven't  yet thought about what to do with that field.
However, if you have a struct  with a lot of fields, and you   don't want to list them all out with  underscores to explicitly ignore them,  
then you can use this `..` syntax to  say "ignore all the other fields".
Tuple-structs, newtypes
Ok so with a struct, you  choose a name for the type,   and you choose names for all the fields. With a  tuple you don't name the type and you don't name  
the fields. What would happen if a struct  and a tuple got together and made a baby?
Then you'd have a tuple-struct! This is a  struct where you choose a name for the type,   but you don't name the fields. It's still  a struct, but it's written with parens  
instead of curly braces, and the fields are  just a comma-separated list without names.
You can access the fields with p.0 and  p.1, just like a tuple. But unlike a tuple,  
this is a distinct type, with a name, and  you can control the interface to that type.
The most common use of tuple-structs is to create  a new type that wraps a single field. When there's  
only one field there's not much point giving  it a name. The point of creating a new type is   to protect against confusion with other types  that have the same underlying representation.
So kilograms and pounds might both be represented  with an f64, but by wrapping them in distinct  
types you can't accidentally use a value  in pounds where kilograms are required.
This practice is called the "newtype" pattern,  and it goes way beyond representing quantities  
with different units. For example, a newtype  might be used to protect a resource, like a file  
descriptor, or a memory allocation, or an amount  of money, or permission to access an I/O port.
We'll talk more about resources in a minute,   I promise. But first, there's one  more kind of struct we need to see.

Deriving Copy and Clone
It's being treated like a resource,  something that should not be copied. Well, of course, a pair of coordinates  representing a point is not a resource,  
it's just plain ol' data, so we'd like to make  this type copyable. How should we do that?
I think the most natural syntax to make a  type copyable would be to say `#[derive(Copy,  
Clone)]`. Nice, that's just intuitive, right?
Ok what the hell is this? Alright well, yes,   this really is the typical Rust syntax to  make a type copyable, so let's break it down.
The hash with square-brackets applies  an attribute to the item that follows,  
in this case the type declaration.  And the "derive" attribute says,   hey compiler, give me the automatic  implementation of some traits on this type.
The "Copy" trait is the one we want,   it's the ability to implicitly make a  copy when a value of this type is used,  
by just making an exact copy of the bytes  that represent the value, like with memcopy.
And, we also need the Clone trait, because  the Copy trait requires the Clone trait.  
Clone is the ability to explicitly  make a copy by calling a clone method,  
which is allowed to do arbitrary  work to construct the new value.   The easiest way to get the Clone trait  is just to derive it, so, there it is.
So now that we've made this struct copyable we  can pass it to the show function as many times  
as we want, and it will implicitly pass  copies around, just like a struct in C.
As for the syntax, I know this looks awkward  at first, but the design makes sense,   we are adding on capabilities to the type.  By default the struct cannot be copied,  
but we can add on the capability to make copies. And you use this derive attribute to  add lots of other capabilities too,  
so a realistic declaration of a Point type would  look like this. Each capability is defined by a  
trait that describes an interface with some  required methods. This derive attribute is a  
very lightweight way to get an automatic  implementation of some traits on a type,  
but it's also very common to implement  traits by hand to customise the behaviour.
Traits are a really important part of the  language, the trait system is very well designed,   and I expect to make multiple videos  on the topic. On the Elements of Rust,  
the map of the type system, the top half  is all the types built into the language,   and the bottom half is all the traits  built into the language. The compiler  
has special knowledge of the Copy  and Clone traits, so here they are.
Clone represents the ability to explicitly  duplicate a value by calling a clone method,  
and Copy represents the ability  to implicitly duplicate a value   by just copying the bytes under the  hood. So, which types are copyable?
All the scalar types are copyable. Arrays are  copyable if the element type is copyable. And btw,  
this language of saying a type "is Copy" is common  for talking about traits in the Rust community,  
but it feels weird to say out loud. Tuples  are automatically Copy if all the fields  
are Copy. Structs and enums are not copyable  by default, but they can explicitly opt in.

Factory functions

Modules and privacy
In a program of any complexity there are many  moving parts, and it's a lot to keep track of.  
The fundamental tool we use to cope with this is  the "separation of concerns". Divide and conquer.  
We try to make clean boundaries  between different parts of a program,   with reusable modules that we  can think about one at a time.
In the code I've shown you so far we've been  doing everything inside a single module,   the root module. To demonstrate private  fields in structs we need another module,  
because privacy is enforced at module boundaries. Our Point type deals with 2-dimensional cartesian  space, so let's make a module called "cartesian".
There are two ways to make a module, and both  use the `mod` keyword with the module's name.  
The first way is to write the body of the  module inline like this, inside curly braces.
The other way is to just declare the module,   and put the code in a separate file. So if  we say "mod cartesian" in the root module the  
compiler will look for the file "cartesian.rs"  or "cartesian/mod.rs". Modules can be nested,  
so you end up with a directory  hierarchy that matches the module tree.
So let's move the Point type declaration  and the impl block into cartesian.rs,  
and we'll keep our main function in main.rs. This is main.rs. We declare the module cartesian,

Destructors, Drop trait
There's one more thing needed to make all  those use cases work well, and that's to   take care of cleaning up the resource when  the object goes out of scope. For that,  
we need destructors, which in Rust  are controlled by the Drop trait.
And oh look, here it is, right  next to the Copy and Clone traits. Destructors are actually quite a  deep topic in Rust. There are some  
interesting cases for the language to handle  when a variable might be valid or might not,   depending on which branch was taken, leading  to something called "drop flags". Destructors  
can have some interesting interactions  with thread unwinding if there's a panic.   And you can't always rely on destructors  running, it is possible to leak objects if  
you try hard enough. So, destruction  is a topic for a whole other video.
We're getting to the end of this one,   but I need to show you one last thing before  we wrap it up with a practice exercise.
References to private fields
What if you have a struct that  holds a resource, like a string,   and you want to let your clients access that  resource without giving up ownership of it?
This is the dynamic String type provided  by the standard library. It's a struct,   and it has private fields  because it manages a resource,  
the heap allocation containing the bytes  of the string. The bytes are on the heap   because the length of the string can change  at runtime. So, the struct contains a pointer,  
and it has a destructor that frees the heap  allocation when the String is destroyed.
String is not copyable, it is a move-only  type, because it owns a resource. If we  
did allow the String struct to be copied,  that would just make a copy of the pointer,   so then there would be two structs both  pointing to the same allocation on the heap.  
That would be bad, because when one  struct frees or reallocates the string,   the other struct would be left with a  stale pointer, leading to a use-after-free.
So I'm using String as an example  of a type that holds a resource.   And now I want to make a struct  that holds a string in a field.
This struct, Video, has a  private field called title,   that holds a String. And because String  cannot be copied, that means Video also  
cannot be copied. If I tried to implement  the Copy trait for Video, I'd get an error.
The title field is private, so to make a Video we  have a factory function called `new` that takes a  
String and returns a Video with that string  in the title field. Also notice I'm using  
another little shortcut here: The field name is  `title` and the variable from the parameter has  
the same name. So I don't have to say `title:  title` to name the field and give it a value,  
I can just say `title` because the local variable  has the same name as the field I'm initialising.
Next I want to provide readonly access to the  field, with a method called title. The title  
method takes self by shared reference,  `&self`. That's the right choice because  
I want the client to be able to read the  title, whether they own the Video object,   or they have exclusive access to it, or even  if they only have a shared reference to it.  
Choosing `&self` here gives my  clients the most flexibility. So, what type should this method return? What do  I give the caller when they want to see the title?
Well, let's try returning a String.  So I say the return type is String,   and in the method body I return self.title.
This does not compile. "Error: cannot move out of  `self.title` which is behind a shared reference."
"The move occurs because  `self.title` has type `String`,   which does not implement the `Copy` trait."
So the compiler sees that we're trying to  return self.title by value, which would  
mean moving it out of the Video struct. And  we can't do that, because, well first of all,  
we can't mutate the Video because we're accessing  it through a shared reference which is read-only.
But even if we take self by mutable reference  with `&mut self`, we get the same error. We  
can't just rip the title String out of the  Video because the Video object still has to   be valid after this method returns. This method  is just borrowing access to the Video struct.
Clone trait, Copy vs Clone vs Move
In both cases the error message goes on to  make a suggestion: "Consider cloning the   value if the performance cost is acceptable."  And it shows us the syntax for doing that:
So the String type doesn't implement Copy, but  it does implement the Clone trait. That's the   one where you call a clone method, that can  do arbitrary work to come up with the new  
instance. In the case of a String, this is  a deep copy. When we call self.title.clone()  
it makes a new heap allocation, and copies all  the bytes to make the new string that we return.
I want to pause here to note, types that  implement the Clone trait are an interesting   half-way point between plain ol' data types that  can be copied, like scalars or the Point struct,  
and resource types that can't be copied. String  implements Clone. It's a resource type in the  
sense that it manages a heap allocation so you  can't just copy the bytes of the String struct,   because then the copies would be fighting over  the same heap allocation. But it's kind of a  
plain ol' data type, it's just a string, and you  can make a copy by cloning it if you need to.
Anyway in this particular case, cloning the  title works, it compiles, but... I don't feel  
great about it. All I want to do is give  the caller readonly access to the string,   surely we don't have to duplicate  the whole string just for that.
Instead of cloning the string and returning  it by value, we can return a shared reference   to the one we already have. So I change the  return type to `&String`, and in the method  
body I say `&self.title`. This is much better,  this is super lightweight, we're just returning  
a pointer to the field. And it's safe, because  at each place where this method is called, the  
compiler tracks the returned pointer. For as long  as the caller holds the pointer to the string, the  
compiler treats the Video as being in a shared,  readonly state. So while it's shared, nobody can  
mess with the Video object or the title string  in any way that would invalidate the pointer.
String vs &str
This is cool, but actually, we're not  done yet. This particular String type  
is one of several options for managing a UTF-8  string, with different tradeoffs. For example,  
there's a copy-on-write string type. Maybe one  day I'd like to change the private field to  
use a different type to store the string, but  right now that would be a breaking change in   the API. I'm exposing to my clients the fact  that I'm using this particular String type.
There is a better option. I can change the return  type to `&str`, all lowercase. This is a shared  
reference to a "string slice", which means it  points directly to the UTF-8 bytes of the string  
in the heap allocation. I don't even have to  change the body of the method, because the String  
type has the ability to automatically coerce the  type. If you have a reference to a String struct,  
you can implicitly turn that into a  reference to a string slice, `str`.
This is better because across all the options  I might choose to store the title string,  
they can all expose their underlying  UTF-8 storage as a string slice. So  
the client no longer knows or cares  which particular String type I'm using.
Separation of concerns is a beautiful thing.  Anyway there's more to say about all that,   and I'm planning a video going into  detail on strings, but for now,  
the point is that you've seen how a struct can  safely provide public access to private fields.
